# v0.7.5 增量：批准前工程审查门槛

## 目标

双模式已经具备工程版本锁、待批准提案、资料引用、企业型号生命周期、结果版本绑定和方法边界，但这些事实分散在不同页面。工程流的关键动作是“批准并执行”，因此在该动作发生前增加一层只读审查汇总：让使用者明确知道当前提案是否仍绑定当前版本，以及哪些输入仍属于研究假设。

## 数据来源

面板只读取已有事实，不调用大模型生成合规结论：

- `StudioProvider`：工程 revision、未提交输入、锁定项和待批准提案版本。
- `/api/enterprise/workspaces/{id}/assessment`：R20 依据、资料引用、企业型号当前生命周期与参数一致性、计算域及方法范围。
- 服务端仍负责真正的 revision lock、产品 binding、参数校验和求解；前端面板不是授权绕过，也不改变批准 API。

## 判定

- **阻断**：提案过期、提案基准版本与当前工程不一致、存在未提交输入。界面已有批准禁用逻辑保持不变，审查面板只解释原因。
- **研究级可执行**：没有阻断项，但存在厂家资料缺失、R20 估算、自定义/失效型号或方法假设。允许现有研究计算继续，但这些边界必须可见。
- **检查完成**：当前版本、输入、资料、型号和方法项目均通过当前摘要检查。该状态仍不等于 IEC 证书、制造数据认证或最终工程签审。

assessment 读取失败不会被伪装成“通过”，也不会另行绕过或强行阻断服务端已有审批；界面显示依据摘要不可读，并保留服务端真实校验。

## 验证

新增纯函数 fixture 覆盖未提交输入、旧版本、过期提案、assessment 加载/失败、已核对型号、项目修改副本和停用型号。真实 Chromium 回归覆盖默认研究输入下的警告可见性、批准仍可用，以及工程 revision 改变后面板与批准按钮同时进入阻断状态。

完整 CI 每个桌面项目增加 1 项浏览器用例；严格矩阵预期更新为 Chromium/WebKit 各 77，四组 Windows 桌面项目各 50，mobile-webkit 保持 11。物理求解内核、本地工程数据、Grok 图片资产和正式版本号均未在本次改动中改变。
